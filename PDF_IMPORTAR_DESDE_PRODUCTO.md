# Importar un diseño desde el PDF legacy de un producto

Variante de [PDF_IMPORTAR_DESDE_PDF.md](PDF_IMPORTAR_DESDE_PDF.md): en vez de subir un PDF a mano, acá se elige un **producto** (y una **variante**, si ese producto tiene más de una temática) y el backend arma el PDF de muestra él solo, a partir de lo que ya está cargado en el sistema viejo (`product_pdf` / vistas de `tematica/*`) — no hay que generar el PDF a mano desde una venta ni subirlo después.

---

## Endpoint

```
POST /product-pdf-designs/import-from-product
Content-Type: application/json
```

| Campo | Tipo | Obligatorio | Descripción |
|---|---|---|---|
| `productId` | id | Sí | Producto con PDF legacy a convertir. |
| `variantId` | id | Solo si el producto tiene más de una temática | La variante (`product_variants.id`) que determina CUÁL temática importar. |
| `name` | string | No | Nombre del diseño nuevo. Si no se manda, usa `"{nombre del producto} (importado)"`. |
| `labelShapeId` | id | No | Forma de etiqueta a asociar (como en el alta normal). |

Respuesta: el `ProductPdfDesign` recién creado (mismo formato que `POST /product-pdf-designs` y que `import-from-pdf`), ya **vinculado** a `productId`/`variantId`.

```json
{
  "success": true,
  "message": "Diseño importado del PDF legacy (139 elementos en 1 página(s))",
  "data": { "id": 15, "name": "...", "data": { "pages": [ ... ] }, "is_published": false, ... }
}
```

Errores (todos `422` salvo el último):
- `"Este producto no tiene un PDF legacy asociado (tabla product_pdf)"` — no hay fila en `product_pdf` para ese `productId`.
- `"Este producto no tiene temáticas cargadas en su PDF legacy"` — la fila existe pero `data.tematicas` está vacío.
- `"Este producto tiene N temáticas distintas — hay que elegir una variante (variantId)..."` — falta `variantId` y hay más de una temática posible.
- `"La variante elegida no tiene una temática asociada en este producto"` — se mandó `variantId` pero ninguna temática matchea su atributo.
- `"No se pudo generar el PDF de muestra: ..."` (`500`) — la vista Blade de esa temática no existe o tiró un error al renderizar.

---

## Qué hace

1. Busca `product_pdf` por `productId` y lee `data.tematicas[]` (cada una trae `name`, `pdf-url` — la(s) vista(s) Blade a usar — y opcionalmente `color-range`/`images`/etc., exactamente lo que ya usa `EtiquetaService::generarEtiquetas()` para una venta real).
2. Si el producto tiene una sola temática, la usa directo. Si tiene varias, matchea `variantId` contra el `attribute_values.id` del primer atributo de esa variante (misma lógica que usa `ProductPdfResolverService::resolveLegacy()` para ventas reales).
3. Genera un PDF **de muestra** con esa temática (nombre placeholder `"NOMBRE APELLIDO"`, sin venta real detrás) usando `EtiquetaService::generarEtiquetas()` — el mismo motor de siempre, solo que con datos de mentira en vez de los de una venta.
   - Ese placeholder se usa a propósito para que, al detectarlo en el resultado, el elemento de texto quede guardado como **`value_mode: "dynamic"`, `dynamic_field: "nombre_apellido"`** — igual que sale en una venta real, no como texto fijo que diga literalmente `"NOMBRE APELLIDO"`.
4. Cada vista que haya generado esa temática (puede ser una o varias, ej. `principal` + `vinilo`) se analiza con `PdfDesignImportService::import()` (igual que `import-from-pdf`) y se agrega como una **página** distinta del mismo diseño.
5. **El texto nunca se superpone con el ícono de la misma celda**: cuando hay ambos, el elemento `text` no ocupa la celda entera (eso lo haría pasar por encima del ícono) — se recorta al espacio libre, igual que hace la tabla HTML del sistema viejo (`<td>ícono</td><td>texto</td>`, lado a lado o apilados según el diseño).
6. **Reconstruye el ícono EXACTO de cada celda** (no una aproximación): las vistas `tematica/principal/*.blade.php` referencian un índice fijo tipo `$plantilla['imagen'][2]` por celda — no es aleatorio, está escrito literal en el `.blade.php`. Leyendo ese archivo y extrayendo esos índices en orden (mismo orden en que dompdf dibuja las celdas), más la misma carpeta `storage/app/pdf/Iconos/Tematicas/{TEMATICA}/` que arma `EtiquetaService::generarEtiquetas()`, se sabe EXACTAMENTE qué archivo SVG va en cada celda. Ese archivo YA está cargado en el catálogo nuevo (`personalization_icons`, ver [database/sql/personalization_icons_tematicas.sql](database/sql/personalization_icons_tematicas.sql) — un ícono por cada archivo de `public/icons/Tematicas/*`), así que el elemento se guarda con el `icon_id` correspondiente — **nunca copiando el SVG como archivo propio del elemento** (`custom_icon_path`/`pdf-element-images`): un mismo ícono de catálogo se reusa en todos los diseños que lo necesiten, sin duplicar archivos.
7. Si para alguna celda no se pudo determinar el archivo exacto (la vista no tiene ese patrón, la temática no tiene carpeta de íconos — pasa con vistas "sin dibujo" —, o el archivo todavía no está cargado en el catálogo), esa celda puntual cae al fallback de antes: buscar en el catálogo un ícono con nombre parecido al de algún archivo de la carpeta, repartiendo los que encuentre entre las celdas sin match exacto. Si tampoco hay fallback, se queda con el placeholder `icon_id: 1`.
7.1. **También matchea la tipografía real de esa vista** (ver sección siguiente) — el texto ya no sale siempre con `font_id: null`.
8. Borra el/los PDF de muestra generados — son solo un paso intermedio, no quedan en disco.
9. Crea el `ProductPdfDesign` **sin publicar** (`is_published: false`) y lo **vincula** al `productId`/`variantId` (`product_pdf_design_products`, con `theme_key = variantId` o `null` si no se mandó).

---

## La tipografía real de la vista, no una genérica

Cada vista legacy tiene su fuente fija en el código (`@font-face` + una clase CSS, ver `resources/views/tematica/**/*.blade.php` y `public/css/etiquetas.css`) — no es aleatoria ni configurable por producto:
- 113 de 115 vistas (`principal/*`, `vinilo/*`, `super-mini/*`, `super-maxi/*`, `maxi/*`, etc.) heredan **Oswald** del CSS compartido, aplicada por igual a TODO el texto.
- Un puñado de vistas (`stars/TRANSFER MAYUSCULA` -> **Antonio**, `stars/TRANSFER BOLD` -> **TitanOne**) declaran la suya propia para el nombre del cliente.

El importador detecta esa familia leyendo el `.blade.php` de la vista (mismo criterio que ya se usa para los íconos: leer el código fuente, no adivinar) y busca una `Typography` del catálogo nuevo con ese nombre (o, si no hay ninguna con ese nombre exacto, por el nombre de archivo original que se subió, ej. `Oswald-Regular.ttf`). Si encuentra match, el texto se guarda con ese `font_id` en vez de `null`.

**Limitación**: si la tipografía detectada (ej. "Antonio", "TitanOne") todavía no está cargada en el catálogo (`typographies`), no hay nada para matchear y el texto queda con `font_id: null` como antes — hay que cargarla una vez en el ABM de tipografías para que, de ahí en más, se matchee sola. Además, se aplica UNA fuente por página/vista a TODO su texto (igual que pasa realmente en casi todas las vistas) — en los pocos casos (`stars/*`) donde el texto secundario (ej. "PEDIDO #") usa una fuente distinta a la del nombre (ahí es Helvetica, sin archivo propio), ese texto puntual puede quedar con la fuente del nombre en vez de la suya — revisar a mano en esos casos específicos.

## Las celdas no quedan sueltas: agrupadas y con "Generar grilla" ya armado

Una temática con varias secciones (ej. Unicornio: maxi 4×4, vertical 6×2, super-maxi 3×2, super-mini 6×3) importa decenas de celdas (fondo+ícono+texto cada una) — para no tener que tocarlas una por una en el editor:

- **`group_id`**: fondo e ícono de UNA celda comparten un `group_id` — en el editor, clickear o mover cualquiera de los dos selecciona/mueve la celda entera de una (igual que si se hubiera generado a mano con "Agrupar selección"). El **texto queda afuera del grupo a propósito**: el editor trata una selección de elementos de distinto tipo como "mixta" y ahí deja de mostrar la sección Tipografía en el panel lateral — si el texto compartiera grupo con el fondo, un clic simple sobre el texto recién importado abriría una selección mixta y no se podría tocar su fuente/tamaño/alineación sin desagruparlo primero a mano.
- **`grids`** (`data.pages[].grids[]`): además, las celdas que comparten tamaño y forma (misma combinación fondo/ícono/texto) se detectan como una grilla y se arma el mismo formato que usa "Generar grilla" en el editor (`PdfGrid`: `cols`, `rows`, `gap_x_cm`, `gap_y_cm`, `template`, `members`) — el diseño importado llega con una entrada de `grids` por cada sección distinta (ej. Unicornio importa 4). Esto permite abrir "Generar grilla" después de importar y cambiar cols/filas/separación de TODA una sección de una, en vez de reacomodar cada celda a mano.
  - El `sig` de cada celda (que el editor usa para saber si una celda fue modificada a mano y no tocarla al reescalar) se calcula con el mismo algoritmo que el front (`PdfDesignHelper.elementSignature`, normalizar+ordenar+hash djb2) — coincide exacto para todo lo que generamos (números, hex, texto en español). Si en algún caso puntual no coincidiera (texto con caracteres fuera del rango normal), lo peor que pasa es que el editor trate esa celda como "ya modificada" y no la toque al reescalar — no rompe ni pierde nada.
  - Esto es **metadata nueva que el backend no usaba hasta ahora** (`EtiquetaService` genera el PDF leyendo `elements` igual que siempre, ignora `grids` por completo) — es pura comodidad para el editor, no cambia en nada cómo se genera el PDF final.
  - **Limitación conocida (del editor, no del importador)**: si las celdas de una sección tienen cada una un color de fondo distinto a propósito (ej. las vistas "COLOR RANGE"), usar "Generar grilla" para cambiar filas/columnas/separación le pisa el color propio de TODAS las celdas por el de la celda molde (template) — "Generar grilla" siempre clona la celda molde, no sabe de colores por-celda. No es algo que el importador pueda evitar desde los datos que manda; el fix real es en `applyGridParams` del editor (ver `useDesignEditor.ts`), para que una celda ya existente conserve su propio color en vez de clonarlo del template al regenerarse.

## Por qué es seguro vincularlo sin publicar

`ProductPdfResolverService::resolveAndGenerate()` solo usa un vínculo si su diseño tiene `is_published = true`. Un diseño recién importado por este endpoint queda sin publicar, así que **no cambia nada en la generación real de ninguna venta** hasta que alguien lo revise en el editor y lo publique a mano — igual que con un diseño armado o importado manualmente. Si ya había otro diseño publicado para ese mismo producto/variante, conviven los dos vínculos sin pisarse: el viejo sigue siendo el que se usa hasta que se publique el nuevo (y ahí sí conviene despublicar o desvincular el anterior).

## Qué NO hace (mismas limitaciones que `import-from-pdf`, salvo el ícono)

- El ícono sale exacto **solo cuando la vista Blade usa el patrón `$plantilla['imagen'][N]`** (las de `tematica/principal/*` lo usan) **y** el archivo correspondiente ya está cargado en `personalization_icons`. Para vistas sin ese patrón (ej. "sin dibujo", gama de colores), o un archivo nuevo que todavía no se cargó al catálogo, cae al fallback por nombre — que sigue siendo aproximado.
- La tipografía (ver sección de arriba) sale exacta **solo si ya hay una `Typography` cargada en el catálogo con ese nombre** — si no, queda con `font_id: null` como antes. Y se aplica una sola fuente por página a todo su texto, así que el texto secundario de las pocas vistas con una fuente distinta para él (`stars/*`) puede necesitar corregirse a mano.
- Las temáticas **"PERSONALIZABLE"** (vistas `tematica/*-and-*/PERSONALIZABLE*`, ej. combos "Maxi - Spot") no tienen un color ni un ícono real detrás — en una venta real el cliente los elige al comprar. El PDF de muestra usa un gris de relleno (`#CCCCCC`) y un ícono cualquiera del catálogo (`icon_id: 1`, el mismo placeholder de siempre) solo para que la vista "con ícono" tenga algo real que dibujar. A diferencia del resto de los campos importados, acá el admin **no** tiene que reemplazar nada a mano: el ícono y el color de cada celda "maxi"/"spot" de una vista "PERSONALIZABLE" salen ya marcados `editable_by_customer: true` (`editable_field: "icon"`/`"color"`) — en una venta real se reemplazan solos por lo que haya elegido el cliente (`EtiquetaService::resolverElementoDesign`), quedando `icon_id`/`color` del PDF de muestra como respaldo si no personalizó nada. Puntualmente: en "maxi" el campo editable por color es el fondo ya fusionado (ver el punto de abajo); en "spot" es el NOMBRE (el círculo no tiene fondo propio en el CSS legacy — el color de `$plantilla` ahí pinta el texto, no un fondo). Si el cliente elige explícitamente no llevar ícono (`customization_data.icon.name === "Sin dibujo"`, ver [PDF_ICONO_PERSONALIZADO.md](PDF_ICONO_PERSONALIZADO.md)), el ícono queda realmente vacío (no cae al `icon_id` de respaldo — fix aparte en `EtiquetaService::resolverElementoDesign`/los controladores de venta, que antes sí caían ahí pese a lo que ya decía ese doc) y el nombre se recentra solo en toda la etiqueta vía `layout_groups` (ver el punto de "maxi" de abajo, `hidden_with_icon_id`). Si el `pdf-url` guardado ya apunta a la variante "SIN ICONO" de la vista, no se simula ningún ícono (ese producto no tiene esa opción) — ahí no hay nada de esto que aplicar, esa vista ya arma una sola etiqueta con el nombre centrado de por sí.
- Las vistas con una fila **"spot"** (celdas circulares — `spot/*`, `spot-and-maxi/*`, `maxi-and-spot/*`, `spot-and-super-mini/*`) no le pintan fondo propio a esas celdas (el "fondo" que se detecta es, en realidad, el color del ícono, y el nombre queda sin alinear con su ícono) — el importador recalcula el fondo de cada una de esas celdas, centrado en el punto medio entre ícono y nombre, con `label_shape_id` apuntando al label_shape circular `"Spot"` del catálogo (así el editor la muestra/recorta como círculo) y recentra el nombre debajo del ícono. El **tamaño** de ese fondo es el tamaño FIJO del label_shape `"Spot"` del catálogo (3×3cm — el mismo que declara `.circulo-personaje` en el CSS de estas vistas), no un cálculo a partir de ícono+texto (eso podía dar un círculo más grande que el real). El nombre también se agrega recién ahí a `data.pages[].grids[]` (no formaba parte de la grilla cuando se armó, más arriba, porque todavía no se sabía qué ícono le correspondía) — sin esto, usar "Generar grilla" en el editor para cambiar cols/filas/separación de una fila "spot" regeneraba bien el fondo+ícono pero dejaba el nombre sin tocar. Además, el `gap_x_cm`/`gap_y_cm` de esa fila (calculado antes, con la posición de los fondos chicos originales) se **recalcula de nuevo** acá, ya con los fondos agrandados a 3×3cm — si no, quedaba un espacio mucho mayor al real entre columnas, y "Generar grilla" terminaba empujando columnas enteras fuera de la hoja al cambiar filas/columnas. El recálculo no compara contra el lado del círculo (3cm) sino contra el rectángulo que realmente engloba fondo+ícono+texto de la celda molde — el nombre es más ANCHO que el círculo (sobresale un poco a los costados, aunque entra bien en alto), así que el "ancho de celda" horizontal que usa el editor al regenerar columnas (`PdfGrid`, ver `applyGridParams` en `useDesignEditor.ts`) es mayor a 3cm; calcular el gap contra 3cm dejaba de más y corría las columnas de su lugar original. El ANCHO de ese nombre, a su vez, se calculaba mal cuando el PDF original lo traía partido en 2 renglones (nombre arriba, apellido abajo — el caso normal en estas vistas circulares): la caja salía tan ancha como "NOMBRE APELLIDO" junto en un solo renglón (bien más ancho que el círculo) en vez de medir el renglón más largo de los dos (ver `PdfDesignImportService::textsToTextElement`) — en el PDF real no pasaba nada raro porque ahí sí se parte en 2 renglones cortos al generarlo (`EtiquetaService::dividirEnRenglones`), pero al editar el texto de muestra en el editor se veía saliéndose del círculo — se corrigió acotando el ancho de ese renglón al renglón más largo real en vez de a la suma de ambos. Pero la caja resultante (lo justo para el nombre/apellido reales) quedaba demasiado angosta para el marcador genérico que muestra el editor cuando el campo todavía no tiene una venta real detrás (`"(x)Nombre y apellido"`, bastante más largo que cualquier nombre real): el editor dibuja esa caja con su ancho real (CSS), no con `max_chars_per_line` (ese límite solo lo usa el backend al generar el PDF real) — así que el marcador se envolvía solo, dentro de esa caja angosta, en 3 renglones feos (hasta la "(x)" sola en su propio renglón). Se agranda la caja al ancho disponible DEL CÍRCULO (no al del nombre real) — sigue sin salirse del círculo (es justo lo que entra adentro) y le da mucho más lugar al marcador para acomodarse en 2 renglones. `max_chars_per_line` también se recalcula geométrico a partir de ese mismo ancho disponible y el tamaño de fuente (cuántos caracteres entran de verdad, no cuántos necesita el nombre de muestra) — nunca se achica, así que un nombre real largo se sigue partiendo bien en el PDF final. El tamaño de letra según longitud del nombre de esta celda circular (`.circulo-personaje p.normal-text-size`/`p.small-text-size`) se arma con el mismo mecanismo genérico que cualquier otro contenedor — ver más abajo, "El tamaño de letra según longitud del nombre se lee directo del CSS de la vista". Por último, cada celda se centraba según la posición real de SU PROPIO ícono en el PDF de origen, que puede traer un corrimiento de 1-2mm sin ningún significado (particularidad de cómo cachea dompdf las métricas de fuente para el primer elemento de una fila, la misma que afecta el `line_height` — ver más abajo) — sin corregirlo, una fila de celdas por lo demás idénticas quedaba con la primera columna visiblemente más arriba o abajo que el resto; ahora cada celda se lleva a la posición mediana de su fila/columna antes de guardar. La MISMA particularidad de dompdf puede afectar, en vez de la posición, el `line_height`/`height_cm` medido del nombre — y ahí la diferencia no es de 1-2mm sino bien visible (ej. una columna entera con el interlineado notoriamente más separado que el resto, mismo texto y tamaño de fuente). Como las 20 celdas son iguales por diseño, se normalizan todas al mismo `line_height`/`height_cm` — y para `line_height` puntualmente no hace falta ni elegir entre lo medido en cada celda: el valor real está literal en el CSS de estas vistas (`detectSpotLineHeight()`, `.circulo-texto { line-height: 0.7 }`, igual en las 4 vistas "spot" con o sin ícono) y se usa directo ahí, exacto, en vez de adivinar con lo medido. Para `height_cm` (y para `line_height` en el caso raro de que la vista no tenga esa regla) se usa la MODA (el valor que más se repite entre las 20, no el promedio) — la idea es "la mayoría está bien medida, la minoría salió con el artefacto de dompdf", no promediar un valor que legítimamente varíe celda a celda. Si todavía no existe un label_shape con ese nombre exacto, no se toca nada (quedan como antes).
- Las vistas **"maxi"** (`maxi/*`, `maxi-and-spot/*`, `spot-and-maxi/*`, `maxi-and-super-mini/*`, etc. — ver `.etiqueta-maxi` en el CSS de esas vistas puntuales) dibujan el ícono y el nombre como DOS celdas de tabla adyacentes, cada una con su propio fondo (una blanca angosta de ~38% del ancho para el ícono, una del color de la temática de ~62% para el nombre, pegadas sin espacio) — el importador las detectaba como DOS grillas separadas del mismo tamaño de celda, sin que ninguna de las dos representara la etiqueta real completa, y ninguna llevaba el label_shape del catálogo "Maxi" (quedaban como rectángulo liso). Si se le asignaba esa forma a cualquiera de los dos fondos por separado, quedaba recortada a la mitad del ancho real y el ícono (que vive en la otra grilla) caía afuera. Ahora se fusionan ambas grillas en una sola, celda por celda: el fondo del nombre pasa a cubrir la etiqueta completa (ícono + texto) y a llevar `label_shape_id` apuntando a "Maxi" del catálogo. El fondo blanco del ícono y el ícono mismo **no se tocan** — se probó primero usar el `fill` nuevo del ícono (ver `PDF_FONDO_ELEMENTOS.md`) para ahorrarse el elemento `background` aparte, agrandando la caja del ícono a toda su zona blanca — pero el ícono se dibuja con `object-fit: contain` (estira la imagen para llenar su caja manteniendo proporción), así que terminaba mucho más grande que en el PDF real (la vista deja harto margen alrededor del ícono a propósito, `.etiqueta-maxi img { height: 1.2cm }` fijo, sin importar el tamaño de la zona — el ícono detectado YA viene más chico que esa zona, es la medida real). Dejando el fondo blanco como elemento aparte se evita el problema sin perder nada visual. El ícono SÍ se redimensiona (se achica o se agranda, lo que haga falta, preservando proporción) contra esa zona blanca: margen fijo chico (0.3cm) SOLO a los costados y casi nada arriba/abajo (0.12cm) — el ícono ocupa prácticamente toda la altura disponible, como en la vista real (`.etiqueta-maxi img { height: 1.2cm }`, una altura fija sin margen vertical de más). Pasa a compartir grupo con el fondo grande (clickear/mover cualquiera mueve la celda entera) y los 4 elementos de la celda (fondo grande, fondo blanco, ícono, texto) se renumeran `z_index` 0-1-2-3 para que el fondo blanco se siga dibujando ARRIBA del fondo grande en su zona, sin importar el orden en que hayan quedado en `elements` (dompdf no respeta un `z_index` no entero tipo 0.5, así que tienen que ser enteros). El nombre se recentra (horizontal y vertical) a mano en la zona libre a la derecha del ícono — se probó primero armar una "Relación" (`layout_groups`, el mismo mecanismo que usa el resto del importador para celdas con un fondo en común) pero esa herramienta centra ícono+texto como UN bloque único en la etiqueta entera: como el bloque es más angosto que la etiqueta completa, el ÍCONO terminaba corrido de su lugar fijo en la zona blanca (se recentraba junto con el texto, en vez de quedarse quieto). Acá el ícono nunca se mueve; el texto lleva en cambio `reflow_with_icon_id`/`reflow_container_id`/`reflow_icon_zone_width_cm`, que `EtiquetaService::ajustarPorIconoAusente()` usa para recentrarlo en tiempo de generación: en la zona libre (etiqueta completa menos la zona del ícono) si el ícono de la venta real está presente, o en la etiqueta ENTERA si no (ahí la zona del ícono, de paso, ya quedó oculta por el punto de arriba). El **tamaño** de esa etiqueta fusionada, a diferencia del punto de arriba con "Spot", NO es el tamaño fijo del catálogo — acá se usa directo el detectado en el PDF de muestra (la unión de los dos fondos originales). La forma "Maxi" del catálogo (`label_shapes` id 2, 4.40×2.40cm) corresponde al `.etiqueta-maxi` de OTRA vista (`principal/SKATE.blade.php`, y el `public/css/etiquetas.css` compartido) donde esa clase es apenas la celda/espaciado de una grilla — ahí el ícono+nombre van centrados chicos adentro, sin fondo de color propio, bien más chicos que 4.40×2.40cm — no el tamaño real de la etiqueta de dos tonos que arman las vistas "PERSONALIZABLE" (acá sí, `.etiqueta-maxi` en su propio `.blade.php` es la etiqueta visible completa, con su propio `width`/`height`: `5.2cm`/`1.9cm`, un valor completamente distinto al de "SKATE" pese a compartir nombre de clase). Usar el tamaño del catálogo agrandaba la etiqueta más de lo que sale en el PDF real. `label_shape_id` igual se asigna a "Maxi" (es solo categoría/metadata para el selector "Forma" del editor — esta forma no tiene `outline_svg`, no dibuja ni recorta nada propio, así que no importa que su tamaño de catálogo no coincida con el de esta celda). El `gap_x_cm`/`gap_y_cm` de esa grilla, calculado originalmente con el ancho/alto del fondo de texto SOLO (más chico), también se recalcula acá ya con las celdas en su tamaño final — mismo motivo y mismo mecanismo que el recálculo de "Spot". Si todavía no existe un label_shape llamado "Maxi", no se toca nada (quedan las dos grillas sueltas, como antes).

  Cuando la vista es "PERSONALIZABLE" (ver punto de arriba), el fondo blanco del ícono trae además `hidden_with_icon_id` apuntando al propio ícono de la celda — un campo nuevo, puntual de este caso, que no forma parte de ningún `layout_groups` (el ícono y el fondo blanco siguen SIN tocarse entre sí, por lo explicado arriba). `EtiquetaService::ocultarFondosDeIconoAusente()` lo revisa después de resolver todos los elementos de la página (antes de `aplicarLayoutGroups`): si el ícono de una venta real queda sin imagen (el cliente no personalizó, o explícitamente "Sin dibujo"), el fondo blanco se oculta (`layout_hidden`, el mismo campo que ya usa `aplicarLayoutGroups` para un miembro ausente — `RENDER.blade.php` lo respeta para CUALQUIER elemento, no solo los de un grupo) justo antes de que el nombre se recentre en el fondo grande — sin esto, el fondo blanco se quedaba ahí aunque el ícono ya no estuviera, y el nombre recentrado terminaba superpuesto a él (invisible en la parte que caía sobre el blanco, al ser texto blanco sobre blanco).
- **El tamaño de letra según longitud del nombre se lee directo del CSS de la vista**, para el texto de CUALQUIER celda de CUALQUIER temática (no solo "spot"): casi todas las ~115 vistas legacy achican la letra a mano cuando el nombre completo es largo (`EtiquetaService::generarEtiquetas` calcula `$fontClass = strlen($nombre) > 20 ? 'extra-small-text-size' : (strlen($nombre) > 16 ? 'small-text-size' : 'normal-text-size')`, una clase que cada vista resuelve con SU PROPIO tamaño en pt según el contenedor — ej. `.circulo-personaje p.normal-text-size { font-size: 12pt }`, `.etiqueta-maxi-text p.small-text-size { font-size: 11pt }`, cada contenedor con los suyos, algunos con 2 niveles y otros con 3). El importador lee esas reglas directo del `.blade.php` (sin hardcodear vista por vista) y, para cada grilla cuya cantidad de celdas coincide con la de un contenedor que varía, le arma a su texto `font_size_rules` (lo que de verdad usa `EtiquetaService::resolverTamanoFuente` al generar el PDF real) y también `length_rules`/`length_rules_enabled` (el toggle "Tamaño por longitud" del editor, con sus reglas ya cargadas — el editor muestra cada una como su propia fila, por eso van las mismas explícitas en los dos lados, con los umbrales reales del `$fontClass` legacy, 16 y 20, en vez de `null` para que el campo "Hasta ___ car." de la última fila no quede vacío). Si el contenedor no define los 3 niveles (la mayoría solo tiene normal/small, sin extra-small), el umbral de la última regla sigue siendo el real (20) — pero el tamaño "de base" del elemento (el que se usa si un nombre se pasa de ese último umbral y ninguna regla matchea) se deja en el de esa ÚLTIMA regla, no en el de "normal": así un nombre larguísimo sigue respetando el último tamaño ya elegido en vez de volver a agrandarse. Un contenedor con un solo tamaño (no varía nunca) se deja sin tocar. Si dos grillas distintas tienen la misma cantidad de celdas (podía pasar con la tabla "maxi" — ver el punto de arriba, ahora ya no llega a este paso con las dos grillas sueltas porque se fusionan antes) se usa la primera que realmente tenga un elemento de texto adentro.
- El nombre del cliente se detecta como dinámico (`dynamic_field: "nombre_apellido"`). El texto "PEDIDO # ..." (pie de página/costado, cuando la temática lo trae) usa el otro mecanismo disponible para esto: queda con `value_mode: "fixed"` pero el número de muestra se reemplaza por el placeholder `{{numero_pedido}}` dentro de `content` (ej. `"PEDIDO # {{numero_pedido}}"`) — el mismo esquema de placeholders que ya resuelve `EtiquetaService::resolverElementoDesign()`, que preserva el prefijo fijo "PEDIDO #" y solo sustituye el número por el de la venta real al generar el PDF.
- No reconoce ni evita duplicados: si se llama dos veces para el mismo producto/variante, crea dos diseños distintos (ambos sin publicar) — conviene borrar el anterior si era una prueba.

## Ejemplo de uso

```bash
# Producto con una sola temática
curl -X POST https://tu-dominio/api/product-pdf-designs/import-from-product \
  -H "Authorization: Bearer {token}" \
  -H "Content-Type: application/json" \
  -d '{"productId": 912}'

# Producto con varias temáticas: hay que indicar la variante
curl -X POST https://tu-dominio/api/product-pdf-designs/import-from-product \
  -H "Authorization: Bearer {token}" \
  -H "Content-Type: application/json" \
  -d '{"productId": 965, "variantId": 1020, "name": "Blanco y Negro (importado)"}'
```

Después de importar, conviene revisar en el editor: los íconos que matchearon exacto (vistas tipo `principal/*` con el archivo ya en el catálogo) ya deberían salir idénticos al PDF original y no necesitan tocarse; los que cayeron al fallback por nombre o al placeholder sí hay que reemplazarlos a mano. En cualquier caso falta asignar tipografías reales y pasar textos a dinámicos donde corresponda (ver [PDF_IMPORTAR_DESDE_PDF.md](PDF_IMPORTAR_DESDE_PDF.md#ejemplo-de-uso)) antes de publicar el diseño.
